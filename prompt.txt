# Project: llm-param-lab (session id: 1675bed8-ba0a-471d-ad23-800c5cf4c746)

Build a Java 21 + Quarkus 3 + Langchain4j 1.x project called `llm-param-lab`.
It's a tool to test a local (or remote) LLM across multiple prompts and
parameter combinations, then evaluate results either against an expected
output or via a second "judge" LLM.

---

## 2. Domain Model (Hibernate entities)

### ModelConfig
- id (Long, auto)
- name (String, unique) — e.g. "my-local-llama"
- provider (enum: OLLAMA, OPENAI_COMPATIBLE)
- baseUrl (String) — e.g. "http://localhost:11434" or "https://api.openai.com/v1"
- apiKey (String, nullable)
- modelName (String) — e.g. "llama3.1" or "gpt-4o-mini"
- isActive (boolean) — which one is the model under test

### TestSuite
- id (Long, auto)
- name (String)
- description (String, nullable)
- expectedOutput (String, nullable) — if set, results are compared to this
- expectedOutputMode (enum: EXACT, CONTAINS, REGEX, NONE)
- judgeModelId (Long, FK to ModelConfig, nullable) — if no expectedOutput, use this model as judge
- judgePrompt (String, nullable) — custom judge prompt; if null, use a default rubric
- createdAt, updatedAt

NOTE: systemPrompt is NOT at suite level. Each TestCase carries its own
systemPrompt. This allows testing different system prompts (agent personas,
tool definitions, etc.) against the same set of user prompts and params.

### TestCase
- id (Long, auto)
- suiteId (Long, FK to TestSuite)
- name (String) — label for this test case
- systemPrompt (String, nullable) — the system prompt for THIS test case.
  If null, no system message is sent (user prompt only).
- userPrompt (String)
- sortOrder (int)

### ParamSweep
- id (Long, auto)
- suiteId (Long, FK to TestSuite)
- paramName (String) — e.g. "temperature", "topP", "maxTokens"
- values (String) — JSON array of values, e.g. "[0.3, 0.5, 1.0]"
  (stored as JSON string; parsed at runtime)

### RunResult
- id (Long, auto)
- suiteId (Long, FK to TestSuite)
- testCaseId (Long, FK to TestCase)
- modelConfigId (Long, FK to ModelConfig)
- paramsJson (String) — the exact parameter combo used, e.g. {"temperature":0.5,"topP":0.9}
- rawOutput (String, CLOB)
- latencyMs (Long)
- tokensIn (Integer, nullable)
- tokensOut (Integer, nullable)
- score (Double, nullable) — 0.0 to 1.0
- scoreReason (String, nullable) — judge's explanation
- evaluationType (enum: EXACT_MATCH, CONTAINS, REGEX_MATCH, JUDGE_LLM, SKIPPED)
- passed (boolean)
- createdAt

## 3. Database Versioning (Liquibase)

Use Liquibase for all schema management. Do NOT use Hibernate ddl-auto.

### Configuration (application.yml)

```yaml

  datasource:
    db-kind: h2
    jdbc-url: "jdbc:h2:file:./data/llmlab;AUTO_SERVER=TRUE"

    ddl-auto: none

    changelog: "db/changelog/db.changelog-master.yaml"
```

IMPORTANT: Every future schema change must be a NEW yaml file in

## 5. Model Factory (core service)

Create a `ModelFactory` service that, given a `ModelConfig`, returns a
`dev.langchain4j.model.chat.ChatLanguageModel` instance:

- If provider == OLLAMA:
  Use `OllamaChatModel.builder().baseUrl(...).modelName(...).build()`

- If provider == OPENAI_COMPATIBLE:
  Use `OpenAiChatModel.builder().baseUrl(...).apiKey(...).modelName(...).build()`

IMPORTANT: The temperature/topP/maxTokens should NOT be baked into the model
builder. Instead, pass them at call time via `ChatRequest` /
`ChatRequestParameters` so the same model instance can be reused across
different parameter combinations.

In Langchain4j 1.x, use:

```java
ChatRequest chatRequest = ChatRequest.builder()
    .messages(messages)
    .parameters(ChatRequestParameters.builder()
        .temperature(0.5)
        .topP(0.9)
        .maxOutputTokens(1024)
        .build())
    .build();
ChatResponse response = model.chat(chatRequest);
```

## 6. Test Runner (core logic)

Create a `TestRunnerService` with method:

```java
public List<RunResult> runSuite(Long suiteId)
```

Logic:
1. Load TestSuite, its TestCases (each with its own systemPrompt),
   its ParamSweeps, and the active ModelConfig.
2. Build the Cartesian product of all parameter values.
   Example: temperature [0.3, 0.5, 1.0] times topP [0.8, 0.95] = 6 combos.
3. For each TestCase times each param combo:
   a. Build messages:
      - If testCase.systemPrompt is not null and not empty:
        add SystemMessage(testCase.systemPrompt)
      - Always add UserMessage(testCase.userPrompt)
   b. Call the model under test with the specific params.
   c. Measure latency, capture token counts from response metadata.
   d. Evaluate:
      - If suite.expectedOutput is not null:
        - EXACT: trim and equals
        - CONTAINS: output contains expected (case-insensitive)
        - REGEX: output matches pattern
        - score = 1.0 if pass, 0.0 if fail
      - Else if suite.judgeModelId is not null:
        - Build judge prompt (from suite.judgePrompt or default from config)
        - Replace {{task}} with testCase.userPrompt
        - Replace {{expected}} with suite.expectedOutput or "N/A"
        - Replace {{response}} with the model's raw output
        - Call judge model
        - Parse JSON response to get score + reason
        - If JSON parse fails, score = null, reason = "judge parse error: ..."
   e. Persist RunResult row.
4. Return all results.

Add a `runAll()` method that iterates all suites.

## 7. REST API (JAX-RS)

### ModelConfig
- GET    /api/models
- POST   /api/models
- PUT    /api/models/{id}
- DELETE /api/models/{id}
- POST   /api/models/{id}/activate  (sets isActive=true, others false)

### TestSuite
- GET    /api/suites
- POST   /api/suites  (body includes nested testCases[] and paramSweeps[])
- GET    /api/suites/{id}  (includes testCases, paramSweeps, latest results)
- PUT    /api/suites/{id}
- DELETE /api/suites/{id}

### Run
- POST   /api/suites/{id}/run        triggers runSuite, returns List of RunResult
- POST   /api/run-all                triggers runAll
- GET    /api/results?suiteId={id}&testCaseId={id}  filter results
- GET    /api/results/summary?suiteId={id}
  returns a summary: for each testCase, the best param combo (highest avg score),
  table of all combos with avg score, min/max latency

### Health
- GET /q/health (built-in)

## 11. Important Implementation Notes

- Use quarkus:dev mode for development. Liquibase auto-runs on startup.
- All REST endpoints return JSON (Jackson).
- The runSuite endpoint should be SYNCHRONOUS (blocking) for simplicity.
  The user will see results when the call returns.
- For the judge call, parse the LLM response as JSON. Be lenient:
  strip markdown code fences, trim, then parse.
- Token counts: Langchain4j ChatResponse.metadata() gives
  TokenUsage with inputTokens/outputTokens if the provider supports it.
  If null, store null.
- Latency: wrap the model.chat() call with System.nanoTime().
- The Cartesian product: use a simple recursive or iterative combinator.
  Store the resulting map as a JSON string in RunResult.paramsJson.
- Add a simple in-memory rate limiter: max 1 concurrent run per suite
  (use a ConcurrentHashMap as a lock).
- The UI is served from META-INF/resources. No separate frontend server needed.
  In dev mode, Quarkus hot-reloads static files.
- The "Run Suite" button in the UI should disable itself and show a spinner
  while the POST is in-flight (it can take 30s+ for multiple param combos).
- CORS is not needed since the UI and API are on the same origin.
- Liquibase: NEVER modify an existing changelog file. Always add a new file
  for schema changes. The master changelog includes them in order.
